## 2.2 当前业务功能

根据代码现状，当前项目的核心功能可以归纳为一个后台权限管理系统雏形，重点围绕以下几个对象展开：

- 用户 `Users`
- 角色 `Roles`
- 权限 `Permissions`
- 登录认证 `Auth`

已具备的主要能力：

- 用户登录、退出、token 校验
- 用户增删改查
- 角色增删改查
- 权限增删改查
- 用户与角色关联
- 角色与权限关联
- Sa-Token 动态角色/权限注入
- Redis 缓存角色与权限结果
- 分页查询与条件查询

因此，当前项目本质上是：

一个基于 `Spring Boot + Jimmer + Sa-Token + MySQL + Redis` 的 RBAC 管理后端。

## 2.3 当前技术架构

当前项目采用的是典型的分层架构：

1. `Controller`
   负责接收 HTTP 请求、参数绑定、返回统一响应。
2. `Service`
   负责业务编排、业务校验、缓存处理、关联关系处理。
3. `Dao`
   负责通过 Jimmer 操作数据库。
4. `Model`
   负责定义实体、DTO 生成规则、查询规格。
5. `Common`
   负责分页、异常、基础实体、工具类等公共设施。

整体请求流大致为：

`HTTP Request -> Controller -> Service -> Dao -> Jimmer SQL -> MySQL`

权限校验流为：

`Request -> Sa-Token -> StpInterfaceImpl -> Redis Cache / DB Query -> Role/Permission Result`

## 2.4 当前逻辑结构特点

当前项目有几个非常鲜明的特征：

### 特征 1：Jimmer 是核心建模方式

项目没有采用传统的：

- `Entity + Mapper XML`
- `Entity + Repository Interface`
- `Entity + 手写 DTO`

而是采用了 Jimmer 的一套建模方式：

- 手写实体接口，如 `Users`、`Roles`、`Permissions`
- 手写 `.dto` 文件，如 `User.dto`、`Role.dto`、`Permission.dto`、`Auth.dto`
- Jimmer 自动生成：
  - `InputView`
  - `View`
  - `Specification`
  - `Table`
  - `Fetcher`
  - `Draft`

这意味着：当前项目实际上已经具备“半自动 DTO 与查询模型生成能力”，这对后续做通用 CRUD 封装非常有利。

### 特征 2：DAO 层已经呈现明显模板化

`UsersDao`、`RolesDao`、`PermissionsDao` 基本具备一致结构：

- `add(...)`
- `update(...)`
- `delete(...)`
- `updateStatus(...)`
- `queryList(...)`
- `queryPage(...)`

三者只是：

- 泛型实体类型不同
- Table 类型不同
- 输入 DTO 不同
- 个别关联操作不同

这说明 DAO 层已经具备抽象成基类或模板的条件。

### 特征 3：Service 层也高度相似

`UsersServiceImpl`、`RolesServiceImpl`、`PermissionsServiceImpl` 也高度一致：

- 创建
- 更新
- 删除
- 获取详情
- 列表/分页
- 状态切换
- 关联对象扩展

这说明 Service 层同样可以继续抽象。

### 特征 4：DTO 并不是手写 Java 类，而是通过 `.dto` 生成

这一点非常关键。

当前 `src/main/dto` 中的 `.dto` 文件定义了：

- 视图返回结构
- 输入结构
- 动态更新结构
- 查询规格结构

例如：

- `User.dto`
- `Role.dto`
- `Permission.dto`
- `Auth.dto`

因此，项目真正的“接口模型定义源头”并不是 Java DTO 类，而是 `.dto` 文件。

这意味着后续封装时，应围绕：

- Jimmer Entity
- Jimmer DTO
- Jimmer Fetcher
- Jimmer Specification

来设计，而不是走传统 MyBatis 风格的 DTO/VO/PO 手写路线。

- 统一版本

## 5.1 模块结构优化

### 建议 1：父工程只做聚合和管理，不做实际依赖承载

推荐父工程保留：

- `modules`
- `properties`
- `dependencyManagement`
- `pluginManagement`

不直接放大批业务依赖。

父工程的职责应该是：

- 管版本
- 管插件
- 管统一规范

而不是：

- 所有模块都默认带上 web/jdbc/security/thymeleaf 等能力

### 建议 2：让 `yi-common` 变成真正的轻量公共模块

`yi-common` 应只保留“跨业务领域也能复用”的能力，例如：

- 分页对象
- 统一响应对象
- 统一异常模型
- 基础枚举
- 基础实体
- 通用工具
- 日志工具

不应默认背上：

- Web 层依赖
- 数据源依赖
- 认证依赖
- 视图依赖

### 建议 3：未来可考虑进一步拆分基础设施模块

如果项目继续扩大，建议逐步演化为：

```text
{projectArtifactId}
|- yi-common-core        公共对象、异常、工具、通用响应
|- yi-common-jimmer      BaseEntity、Jimmer 相关公共定义
|- yi-infra-security     Sa-Token、鉴权、缓存清理工具
|- yi-infra-db           数据源、Jimmer 配置、数据库基础设施
|- yi-admin              管理后台业务模块
```

当前项目规模还不一定必须拆到这一步，但思路是正确的。

- controller
- service
- dao

对于中小型项目这是可以接受的，但随着业务增长，会出现问题：

- 用户相关逻辑分散在多个目录里
- 角色相关逻辑分散在多个目录里

|  |- controller
|  |- service

## 5.3 层次边界优化

### 建议 1：接口层不要直接强绑定框架响应对象

当前控制层大量直接返回 `SaResult`。

这会带来一个问题：

- 业务接口层和 Sa-Token 工具类耦合较重

更理想的方式是：

- Controller 层负责将业务结果包装成统一响应
- Service 层只返回业务对象
- 统一响应格式尽量由项目自己的 `ApiResponse<T>` 控制

这样以后即使不用 Sa-Token，也不会影响整个 API 响应层。

### 建议 2：Service 接口上不需要标注 `@Service`

当前 `UsersService`、`RolesService`、`PermissionsService`、`AuthService` 接口上标了 `@Service`。

通常只需要在实现类上标 `@Service` 即可。

接口层加这个注解没有明显收益，反而会让职责表达不够清晰。

### 建议 3：异常处理应分层更清晰

当前有 `BusinessException`，这是好的。

但全局异常处理器里没有明显针对 `BusinessException` 做专门转换，这会导致：

- 业务异常码可能无法统一透出
- 最终返回格式不够稳定

建议增加：

- `@ExceptionHandler(BusinessException.class)`

专门处理业务异常。

### 建议 4：控制器里的参数一致性要更严谨

例如当前一些接口存在路径参数 `id` 与请求体对象中的 `id` 关系不够严格的问题。

建议统一规则：

- 只要 URL 上有 `{id}`，就以 URL 为准
- 请求体中的 `id` 由 Controller 统一注入
- Service 层不信任前端传入的对象内 `id`

## 5.4 公共能力封装优化

### 建议 1：RBAC 缓存清理应抽成独立组件

当前缓存 key 字符串散落在：

- `RolesServiceImpl`
- `PermissionsServiceImpl`
- `StpInterfaceImpl`

建议封装成统一组件，例如：

- `RbacCacheKeyBuilder`
- `RbacCacheService`
- `RbacCacheCleaner`

职责可以拆成：

- 构造 key
- 删除单个用户角色缓存
- 删除单个角色权限缓存
- 批量清理受影响缓存

这样好处是：

- key 规则不再散落
- 后续更换缓存实现更方便
- 不容易写错前缀

### 建议 2：状态更新能力可以抽成通用能力

当前三个 DAO 都有：

- `updateStatus(id, status)`

三个 Service 都有：

- `enableXxx(id)`
- `disableXxx(id)`

这类逻辑非常适合抽象为：

- `StatusUpdatableRepository`
- `StatusManageService`

### 建议 3：分页能力已经抽出，但还可以继续沉淀

现在已经有 `PageUtils`，这是很好的开始。

可以继续进一步抽象为：

- 统一的分页排序字段校验
- 默认排序策略
- 非法排序字段白名单机制

这样可以避免前端随意传排序字段带来风险。

### 建议 4：密码处理应升级为安全组件

当前使用 `MD5Utils` 处理密码。

这在现代系统里并不推荐，建议改为：

- `BCryptPasswordEncoder`
- `Argon2PasswordEncoder`

并将密码处理封装成：

- `PasswordService`
- `PasswordEncoderAdapter`

这样可以做到：

- 登录校验统一
- 修改密码统一
- 后续算法升级统一

## 7.1 哪些能力适合抽象成通用 CRUD

- 模板方法

## 7.4 DAO 层抽象方案

当前三个 DAO 已经很像，可以抽成类似下面的结构。

```java
public abstract class BaseJimmerDao<E, ID, T> {

    protected final JSqlClient sql;
    protected final T table;

    protected BaseJimmerDao(JSqlClient sql, T table) {
        this.sql = sql;
        this.table = table;
    }

    public abstract Class<E> entityType();

    public <I extends Input<E>> E add(I input, Fetcher<E> fetcher) {
        return sql.getEntities()
                .saveCommand(input)
                .setMode(SaveMode.INSERT_IF_ABSENT)
                .execute(fetcher)
                .getModifiedEntity();
    }

    public <I extends Input<E>> E update(I input, Fetcher<E> fetcher) {
        return sql.getEntities()
                .saveCommand(input)
                .setMode(SaveMode.UPDATE_ONLY)
                .execute(fetcher)
                .getModifiedEntity();
    }

    public void delete(ID id) {
        sql.getEntities()
                .deleteCommand(entityType(), id)
                .setMode(DeleteMode.AUTO)
                .execute();
    }
}
```

然后具体 DAO 只保留差异：

- 实体类型
- Table 类型
- 特殊查询
- 特殊关联操作
- 特殊状态字段操作

例如：

- `UsersDao` 只负责 `updatePassword`、`updateRole`
- `RolesDao` 只负责 `updatePermission`
- `PermissionsDao` 只负责树结构或关联查询

这样 DAO 层重复代码会明显下降。

## 7.5 Service 层抽象方案

可以设计一个基础 CRUD 服务基类：

```java
public abstract class BaseCrudService<
        E,
        ID,
        C,   // CreateInput
        U,   // UpdateInput
        S    // Specification
        > {

    public abstract E create(C input);

    public abstract E update(U input);

    public abstract void delete(ID id);

    public abstract E getById(ID id);

    public abstract List<E> list(S specification);

    public abstract PageResult<E> page(PageQuery pageQuery, S specification);
}
```

进一步推荐不要只做“接口空壳”，而是做“模板方法基类”：

```java
public abstract class AbstractCrudService<
        E, ID, C, U, S
        > implements BaseCrudOperations<E, ID, C, U, S> {

    protected abstract BaseRepository<E, ID, C, U, S> repository();

    protected void beforeCreate(C input) {}
    protected void afterCreate(E entity) {}
    protected void beforeUpdate(U input) {}
    protected void afterUpdate(E entity) {}
    protected void beforeDelete(ID id) {}
    protected void afterDelete(ID id) {}

    @Override
    public E create(C input) {
        beforeCreate(input);
        E entity = repository().create(input);
        afterCreate(entity);
        return entity;
    }
}
```

这套模式非常适合当前项目，因为：

- 基础 CRUD 可以统一
- 具体业务可以重写 Hook
- 缓存清理、领域校验可以放在 Hook 中

例如：

- `RolesServiceImpl` 在 `afterUpdate` 里清权限缓存
- `UsersServiceImpl` 在 `beforeChangePassword` 里校验旧密码

---

## 7.6 Controller 层抽象方案

Controller 层也可以抽象，但建议谨慎抽象。

因为 Controller 除了 CRUD 外，还涉及：

- URL 风格
- 权限注解
- 参数绑定方式
- 返回包装格式
- REST 语义差异

如果项目接口风格稳定统一，可以做一个基础控制器：

```java
public abstract class BaseCrudController<
        E, ID, C, U, S
        > {

    protected abstract CrudService<E, ID, C, U, S> service();

    @PostMapping
    public ApiResponse<E> create(@RequestBody C input) {
        return ApiResponse.success(service().create(input));
    }

    @PutMapping("/{id}")
    public ApiResponse<E> update(@PathVariable ID id, @RequestBody U input) {
        bindId(id, input);
        return ApiResponse.success(service().update(input));
    }
}
```

但更推荐的现实做法是：

- 先抽 DAO 和 Service
- Controller 保持轻量手写

原因是：

- Controller 代码量本来就不大
- 过度抽象 Controller 往往会降低可读性

## 7.7 更适合当前项目的最终方案

结合当前项目，我更推荐下面这套方案：

### 第一层：通用 Repository 抽象

统一：

- 新增
- 更新
- 删除
- 详情
- 列表
- 分页

### 第二层：通用 CrudService 抽象

统一：

- create/update/delete/get/list/page

### 第三层：能力型接口扩展

不要把所有扩展都塞进一个基类，而是按能力拆接口：

- `StatusManageable`
- `RoleAssignable`
- `PermissionAssignable`
- `PasswordManageable`
- `CacheRefreshable`

例如：

```java
public interface StatusManageable<ID> {
    void enable(ID id);
    void disable(ID id);
}
```

这样做比“大而全基类”更容易维护。

### 第四层：Hook 扩展点

在抽象基类中预留：

- `beforeCreate`
- `afterCreate`
- `beforeUpdate`
- `afterUpdate`
- `beforeDelete`
- `afterDelete`

这样具体服务实现类只处理差异逻辑。

## 7.10 这一类抽象需要注意的边界

虽然可以抽象，但不要过度抽象。

建议坚持以下原则：

### 原则 1：先抽象共性，不抽象差异

不要把认证、缓存、树结构、复杂关系维护硬塞进基类。

### 原则 2：抽象层数不要过深

一般控制在：

- 基础 DAO
- 基础 Service
- 可选基础 Controller

即可。

### 原则 3：优先组合，其次继承

比如缓存清理、状态更新、密码处理，更适合能力组件组合，而不是无限继承。

### 原则 4：围绕 Jimmer 设计，不要和 Jimmer 对着干

当前项目最大的优势就是 Jimmer 自动生成 DTO 与查询模型。

后续封装设计要充分利用：

- `Input<E>`
- `View<E>`
- `Fetcher<E>`
- `Specification<E>`

而不是重新回到手写 POJO 全覆盖的老路。

## 11. 一句话总结

当前项目已经不是“从零开始搭架子”的阶段，而是已经进入：

**可以从可运行原型，向可维护工程化框架演进的阶段。**

最值得优先推进的事情有三件：

1. 把依赖从父工程下沉到具体模块。
2. 把通用 CRUD 从 DAO/Service 层继续抽象出来。
3. 把安全、配置、缓存、异常这些横切能力做成稳定公共设施。

做到这三点后，这个项目会从“能用”明显提升到“可持续扩展、可持续维护”。
